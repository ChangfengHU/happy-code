# Git 智能提交指南

本 Skill 旨在使智能体能够在执行开发任务时，以“专家程序员”的视角自主决策 Git 提交的时机和结构。

## 1. 提交点判断逻辑 (When to Commit)

在满足以下任一条件时，智能体应主动评估并向用户建议进行提交：

- **原子任务完成**：当 `todo` 列表中的一个独立子任务（Subtask）被标记为 `completed` 且代码处于稳定状态。
- **阶段性成果**：实现了一个完整的功能函数、修复了一个明确的 Bug、或完成了一组相关的文档更新。
- **重大风险前**：在开始大规模重构或高风险修改之前，应建议先提交当前已验证的稳定状态。
- **环境切换/暂停**：如果任务需要跨越较长时间或正在等待用户反馈，建议保存当前进度。

**决策检查清单：**
1. 代码是否通过了基本的语法检查/编译？
2. 是否运行了相关的测试并确认通过？
3. 变更是否具有原子性（即不包含不相关的杂事）？

## 2. 合并提交判断逻辑 (When to Squash)

在建议提交前，智能体应检查最近的未推送（Unpushed）提交记录，评估是否需要使用 `git commit --amend` 或交互式变基进行合并：

- **修复性提交 (Fixups)**：如果之前的提交是针对同一功能的简单修复（如：修复拼写错误、格式调整、遗漏的文件），应建议合并。
- **实验性迭代**：如果连续几个提交都是为了达成同一个目标而进行的试错（WIP 提交），应在最终目标达成后建议合并为一个清晰的功能提交。
- **逻辑关联性**：如果当前的变更与上一个提交在逻辑上不可分割，且合在一起能提供更清晰的历史上下文，应建议合并。

## 3. 交互流程

1. **状态分析**：运行 `git status` 和 `git diff` 总结当前变更。
2. **规则评估**：基于上述规则判断是否建议提交或合并。
3. **提出方案**：以简洁的语言告知用户决策理由，并提供建议的提交信息。
   - *示例：* “我已经完成了登录逻辑的单元测试，目前代码运行稳定。考虑到前两次提交是中间过程的 Fixup，我建议将它们合并并提交为：'feat: add unit tests for auth flow'。您是否同意？”
4. **执行动作**：在用户确认后执行对应的 Git 命令。

## 4. 提交信息规范

- 遵循项目的提交规范（如 Conventional Commits）。
- 优先解释“为什么”而不是“做了什么”。
- 如果进行了合并提交，提交信息应涵盖所有合并内容的精华。
